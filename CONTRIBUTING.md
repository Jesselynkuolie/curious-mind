
# Contributing to Curious Mind — AI Overview

Thank you for contributing to **Curious Mind — AI Overview**, an educational project that introduces learners to artificial intelligence (AI), machine learning, generative AI, real-world applications, responsible use, and practical AI skills.

This guide explains how team members should contribute content, collaborate, review changes, maintain quality, and prepare the project for submission.

## 1. Project Purpose

The purpose of this project is to create an accessible, accurate, well-organized introduction to AI for beginner learners.

The project aims to:

- Explain fundamental AI concepts using clear, beginner-friendly language.
- Demonstrate the relationship between AI, machine learning, and generative AI.
- Explore practical applications and limitations of AI.
- Teach learners to recognize risks and use AI responsibly.
- Provide structured learning materials, examples, activities, and assessments.
- Maintain a consistent, accessible, and well-documented learning experience.

All contributions should support these educational goals and align with the course requirements.

## 3. Contribution Principles

All contributors should follow these principles.

### 3.1 Accuracy

- Use credible and relevant sources for factual claims.
- Check definitions, examples, dates, statistics, and technical explanations.
- Do not invent references or present unverified information as established fact.
- Explain uncertainty and limitations where relevant.
- Correct errors when they are identified.

### 3.2 Clarity

- Write for learners who are new to AI.
- Define technical terms when they first appear.
- Prefer concise explanations and concrete examples.
- Use headings, lists, tables, and short paragraphs where appropriate.
- Avoid unnecessary jargon and unexplained abbreviations.

### 3.3 Educational Value

- Ensure each chapter has a clear purpose.
- Connect explanations to the chapter's learning objectives.
- Include examples that help learners apply the concepts.
- Add activities or knowledge checks where appropriate.
- Provide answer explanations so learners understand why an answer is correct.

### 3.4 Responsible AI

- Explain the limitations of AI systems where relevant.
- Address privacy, fairness, reliability, and safety when appropriate.
- Do not assume that AI-generated information is accurate.
- Verify AI-assisted content before incorporating it into the project.
- Follow course rules for AI assistance and disclosure.

### 3.5 Accessibility and Inclusion

- Use respectful, inclusive language.
- Explain concepts without assuming advanced technical knowledge.
- Use meaningful headings and descriptive link text.
- Provide useful alternative text for informative visuals.
- Do not rely on color alone to communicate important information.
- Use readable tables and consistent formatting.

## 4. Essential Course Requirements

The following requirements are priorities for the project because they demonstrate that the learning materials form a complete educational resource.

### 4.1 Complete Content Structure

The file `content/00-module-outline.md` should provide a coherent overview of the entire course, including:

- Course purpose and intended audience.
- Prerequisites or assumed prior knowledge.
- Course-level learning objectives.
- The complete module and chapter sequence.
- A brief description of each chapter's purpose and main topics.
- Chapter-level learning objectives.
- The intended learning sequence and connections between chapters.
- Planned learning activities and assessments.
- Relevant supporting materials, where applicable.

The outline should agree with the actual repository contents. Do not describe an activity, resource, or chapter as complete if it has not been created or reviewed.

### 4.2 At Least One Fully Developed Demonstration Chapter

At least one chapter should demonstrate the intended standard for the complete learning materials.

A fully developed chapter should normally include:

1. Chapter title and overview.
2. Clear, measurable learning objectives.
3. Detailed teaching content.
4. Examples or explanations that support understanding.
5. Practical activities or applications.
6. Knowledge-check questions or another appropriate assessment.
7. Correct answers and explanations where applicable.
8. A chapter summary.
9. A glossary of important terms, where useful.
10. Credible references and further reading.
11. Accessibility considerations for included learning materials.

The selected demonstration chapter should be consistent with the module outline and should be reviewed before being described as complete.

## 5. Writing and Formatting Standards

Project documentation should use Markdown unless a different format is required.

### 5.1 Headings

Use a logical heading hierarchy:

- `#` for the document title.
- `##` for major sections.
- `###` for subsections.
- `####` only when an additional level is genuinely necessary.

Avoid skipping heading levels without a clear reason.

### 5.2 Lists and Tables

- Use numbered lists for ordered procedures.
- Use bullet lists for related items without a required sequence.
- Use tables when comparing related information.
- Keep tables readable and avoid overly wide layouts.
- Introduce a table or list when its purpose is not immediately obvious.

### 5.3 Code and Technical Examples

- Use fenced code blocks for code or commands.
- Specify a language identifier when appropriate, such as `python` or `bash`.
- Explain the purpose of technical examples.
- Review code for correctness, security, and suitability before including it.

Programming examples are only necessary when they support the learning objectives.

### 5.4 Links

- Use descriptive link text.
- Check that links lead to the intended resources.
- Prefer original or authoritative sources for important factual claims.
- Avoid relying on a link title or search-result snippet without checking the source.

## 6. Research, Citations, and References

Contributors must document sources for important factual, technical, and research-based claims.

### Recommended practices

- Prefer primary research, official documentation, recognized standards, and reputable educational sources where appropriate.
- Confirm that cited sources actually support the claims made.
- Verify author names, titles, dates, and links.
- Follow the citation style required by the instructor.
- Keep references consistent across chapters.
- Distinguish factual evidence from recommendations, opinions, and illustrative examples.
- Record image, audio, video, and other external asset sources in `assets/asset-register.md`.

Do not invent citations or claim that a source supports a statement without checking it.

When AI tools assist with drafting, contributors remain responsible for reviewing the content and references before submission.

## 7. Responsible Use of External and AI-Generated Materials

Contributors should use external materials only when their use is appropriate and permitted.

Before including an external image, diagram, audio clip, video, dataset, or other asset:

1. Identify the original source and creator when available.
2. Check the license or usage terms.
3. Confirm whether attribution is required.
4. Record the relevant information in `assets/asset-register.md`.
5. Provide alternative text or other accessibility support where appropriate.

For AI-assisted material:

- Follow the instructor's rules and the applicable tool terms.
- Verify factual claims and citations.
- Review outputs for bias, inaccuracies, and misleading statements.
- Respect privacy and avoid sharing unnecessary sensitive information.
- Disclose AI assistance when required by the course or institution.
- Do not misrepresent AI-generated work as independently completed work when that would violate the assignment rules.

## 8. Recommended Contribution Workflow

Use the following workflow for meaningful changes.

### Step 1: Identify the Task

Review `tasks.md`, `review/review-notes.md`, and the relevant project file.

Clarify the intended outcome and check whether the task has already been completed by another contributor.

### Step 2: Review Existing Content

Read the relevant chapter or document before editing it.

Check the module outline and related resources so that new material does not conflict with existing explanations or learning objectives.

### Step 3: Make a Focused Change

- Edit the relevant file rather than creating unnecessary duplicates.
- Keep the change focused on the task.
- Preserve useful existing content unless it needs correction or replacement.
- Use consistent terminology and Markdown formatting.

### Step 4: Review the Change

Before committing, check:

- Accuracy and completeness.
- Alignment with learning objectives.
- Spelling, grammar, and readability.
- Heading structure and Markdown rendering.
- Links and citations.
- Accessibility and responsible-use considerations.
- Consistency with related project files.

### Step 5: Commit the Change

Use a clear commit message that describes what changed.

Examples:

- `docs: complete module outline`
- `content: expand responsible AI chapter`
- `content: add practical prompting activity`
- `review: record chapter feedback`
- `assets: document visual sources`

Choose a message that accurately describes the work performed.

### Step 6: Record Completion and Feedback

- Update `tasks.md` only after the relevant work is actually complete.
- Record review findings in `review/review-notes.md`.
- Record actual meeting decisions in `meeting-notes/meeting-notes.md`.
- Add outstanding issues to the relevant task or review record.
- Do not mark unverified work as approved.

## 9. Review and Quality Assurance

Contributors should review changes before the final submission.

### Content Review

Check that:

- The content is accurate and understandable.
- Learning objectives are addressed by the teaching content.
- Examples are relevant and appropriate.
- Activities are possible to complete using the provided instructions.
- Assessment questions match the concepts taught.
- Answer keys are correct and include explanations where appropriate.
- References are relevant and accessible.

### Repository Review

Check that:

- Files are saved in the intended directories.
- File names follow the existing naming convention.
- Markdown renders correctly on GitHub.
- Links and referenced files exist.
- There are no unnecessary duplicate or contradictory sections.
- Supporting materials agree with the module outline.
- Completion statuses reflect actual progress.

### Final Submission Review

Before submitting, confirm that:

- The course structure is complete.
- At least one demonstration chapter is fully developed and reviewed.
- Supporting materials align with the learning objectives.
- Relevant sources and assets are documented.
- Required activities and assessments are included.
- Review feedback has been addressed or documented.
- The repository has been checked against the teacher's rubric.
- All team members have fulfilled or reported their assigned responsibilities.

## 10. Team Responsibilities

Team members should coordinate their work, communicate progress, and help maintain consistency across the repository.

The following responsibilities describe functional roles. Use the actual approved team assignments when recording ownership.

| Role | Main responsibilities |
|---|---|
| Project Coordinator | Coordinates priorities, tracks overall progress, and checks alignment with assignment requirements |
| Repository and Submission Lead | Maintains repository organization, checks required files, and coordinates submission readiness |
| Content Lead | Reviews educational content, learning objectives, clarity, and consistency across chapters |
| Visual Design Lead | Coordinates diagrams, presentation design, visual consistency, and accessibility |
| Video Lead | Coordinates video planning, script, storyboard, and related production materials |
| Quality Lead | Coordinates quality checks, records feedback, and tracks corrective actions |

These roles support collaboration rather than removing shared responsibility. Every contributor should check their own work and communicate issues that affect the wider project.

Record actual assignments, decisions, and progress in the relevant project documents. Do not treat a proposed assignment as confirmed until the team has agreed to it.

## 11. Communication and Meetings

Team communication should be clear, respectful, and focused on the project.

Recommended practices:

- Share progress and obstacles in a timely manner.
- Identify tasks that depend on other team members' work.
- Discuss significant changes to the course structure before making conflicting edits.
- Record decisions and action items in `meeting-notes/meeting-notes.md`.
- Give specific, constructive feedback.
- Raise unresolved issues early enough for the team to address them.
- Confirm ownership and deadlines for agreed actions.

Meeting records should reflect actual discussions and decisions. Do not invent attendance, meeting dates, agreements, or completed actions.

## 12. Handling Feedback and Errors

Feedback should help improve the learning materials.

When a problem is identified:

1. Describe the issue clearly.
2. Identify the affected file or section.
3. Explain why the issue matters.
4. Propose a correction when possible.
5. Assign responsibility for follow-up when appropriate.
6. Review the correction after it is made.
7. Record the outcome in `review/review-notes.md`.

Prioritize issues that affect required deliverables, factual accuracy, safety, learning objectives, or the ability to complete an activity.

If a problem cannot be resolved before submission, document it honestly rather than marking it as complete.

## 13. Project Status and Documentation

Project documents should provide an accurate picture of progress.

- Use `tasks.md` to track work that remains to be done and work that has been verified.
- Use `review/review-notes.md` to record review criteria, feedback, and corrective actions.
- Use `meeting-notes/meeting-notes.md` to record real meetings, decisions, and assigned actions.
- Use `assets/asset-register.md` to document the sources and licenses of included assets.
- Use `AUDIT-REPORT.md` to record audit findings and follow-up actions where applicable.

A file's existence does not prove that it has been reviewed or approved. Status labels and checkboxes must reflect actual evidence.

## 14. Definition of Done

A contribution can be considered ready for review when:

- [ ] The change addresses the intended task.
- [ ] The content is accurate and appropriate for the intended audience.
- [ ] The change follows the repository's formatting conventions.
- [ ] Relevant learning objectives and assessment requirements are addressed.
- [ ] Sources and assets are documented where needed.
- [ ] Links, spelling, and Markdown rendering have been checked.
- [ ] Accessibility and responsible-use considerations have been addressed.
- [ ] Related files have been checked for consistency.
- [ ] Review feedback has been resolved or documented.
- [ ] The change has been committed to the correct file.

Mark the contribution as approved only after the required review has taken place.
